Task 1: Order List – Analysis

In this task, I implemented a singly linked list to manage restaurant orders. Each order contains an order ID, customer name, table number, item count, and order time. The OrderList class provides methods to add, remove, search, and display orders.

The time complexity of adding an order is O(n) because the program traverses the list to find the last node before inserting the new order. Removing an order also has O(n) time complexity because the program may need to search through the list to find the specified order ID. Similarly, finding an order takes O(n) time in the worst case because the program checks nodes one by one until it finds the requested order or reaches the end of the list.

A linked list is useful for restaurant order management because the number of orders can change frequently. New orders can be added, and existing orders can be removed without shifting elements as in an array. Each node stores an order and a reference to the next node, allowing the list to grow dynamically.

To test the implementation, I added five orders, removed order 103, searched for order 104, and displayed the final list. The output showed that order 103 was successfully removed, order 104 was found, and four orders remained in the list.

This task helped me understand how linked lists work and how their time complexity affects basic data management operations.


Task 2: Food Request Queue – Analysis

In this task, I implemented a queue using a linked list to manage food preparation requests. The queue follows the First-In, First-Out (FIFO) principle. This means that the first request added to the queue is the first one processed. The FoodQueue class includes enqueue, dequeue, size, and printQueue methods.

The enqueue operation takes O(1) time because a new request is added directly at the rear of the queue. The dequeue operation also takes O(1) time because the request is removed directly from the front. The size operation takes O(1) time because the queue maintains a counter that is updated whenever a request is added or removed. Printing the entire queue takes O(n) time because every request must be visited.

A queue is suitable for food preparation because requests should generally be handled in the order they arrive. This makes the process fair and predictable. A stack would be less appropriate because it follows the Last-In, First-Out (LIFO) principle. Using a stack could cause the newest request to be processed before older requests, delaying customers who ordered earlier.

To test the implementation, I added eight food requests and processed the first three. The program removed requests 201, 202, and 203 in the correct FIFO order. Five requests remained in the queue.

This task demonstrated how a queue can organize tasks that need to be processed in arrival order.


Task 3: Completed Order Stack – Analysis

In this task, I implemented a stack using a linked list to store completed order records. Each record contains an order ID, customer name, and completion time. The CompletedOrderStack class provides push, pop, peek, size, and printStack methods. The stack follows the Last-In, First-Out (LIFO) principle, meaning that the most recently added record is the first one removed.

The push operation takes O(1) time because a new record is inserted at the top of the stack. The pop operation also takes O(1) time because it removes the top record directly. The peek operation takes O(1) time because it accesses the top record without removing it. Printing all records takes O(n) time because every node must be visited.

A stack is useful when the system needs to access the most recently completed orders first. For example, it can support reviewing recent completions or implementing a simple undo history. If a queue were used instead, records would be removed in the order they were added. This would make it less convenient to access the most recent record first.

To test the implementation, I added five completed order records, checked the most recent record using peek, and removed two records using pop. The program correctly displayed order 305 as the top record, removed orders 305 and 304, and left three records in the stack.

This task helped me understand the LIFO principle and how a stack can be implemented efficiently with a linked list.


Task 4: Restaurant System Integration – Analysis

In this task, I integrated the linked list, queue, and stack into a single Restaurant System. The system manages active orders, food preparation requests, and completed order records. The RestaurantSystem class provides methods to add orders, add food requests, process requests, add completed records, and display the system state.

The linked list stores active orders and allows the system to add, find, and remove orders. The queue manages food preparation requests using the FIFO principle, ensuring that earlier requests are processed first. This is important in a restaurant because requests should generally be handled in the order they arrive. The stack stores completed order records using the LIFO principle, making the most recently added record accessible first. Combining these data structures allows each part of the restaurant system to use an appropriate method of organizing data.

I also implemented Bubble Sort to sort active orders by order time. The algorithm compares adjacent elements and swaps them when they are in the wrong order. In this implementation, sorting takes O(n²) time in the average and worst cases, where n is the number of active orders. The sorting method operates on an array created from the linked list, so it displays the sorted results without changing the original linked list order. This separation helps preserve the original data while allowing the system to present orders in a useful sequence.

To test the integrated system, I added ten orders and five food requests. I then processed four requests, added two completed order records, and displayed the remaining active orders sorted by order time. The output showed six active orders, one remaining food request, and two completed records. These results helped verify that the main data structures worked together and that processing requests updated the system as expected.

This task demonstrated how multiple data structures and a sorting algorithm can work together in one application. It also helped me understand how to organize different types of data according to their purposes. In a larger restaurant application, this design could be extended with features such as order status updates, preparation-time estimates, and more detailed reports. Overall, the integration made the program more organized and easier to test.
